# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Next.js 15 (App Router) + React 19 web app used to control the grill in real time and manage cooking programs, plus the REST API those programs are stored through (`src/app/api/`, on MariaDB). It runs as a Node server in Docker on the home lab. Part of the larger GaztaindiGrill ecosystem — see `../CLAUDE.md` for how this fits with the firmware, and for the MQTT topic source of truth.

## Commands

```bash
npm run dev      # next dev --turbopack
npm run build
npm run start
npm run lint      # next lint
npm run typecheck # tsc --noEmit, does not touch .next
```

**Deploying** is Docker on the home lab: `output: 'standalone'` in `next.config.ts`, a multi-stage
`Dockerfile` and `compose.yaml`, rebuilt on the LXC with `git pull` + `docker compose up -d --build`.
[docs/deploy.md](docs/deploy.md) is the full runbook, Docker install included. `docker build .` also
works on the dev machine (about 4 min) and, unlike `npm run build`, never touches the dev server's `.next`.

**Configuration is server-side and read at runtime**, from `.env.local` in dev and `.env` next to
`compose.yaml` on the server; `.env.example` lists every variable. `DB_*` point at MariaDB, `MQTT_*`
at the broker. Nothing is `NEXT_PUBLIC_*` any more, so the image holds no host or credential, and the
root layout calls `connection()` so pages render per request rather than freezing the build's
environment. Changing a value needs a restart (`npm run dev` included), never a rebuild.

**Do not run `npm run build` while `npm run dev` is up.** `next dev` uses Turbopack and `next build` uses webpack, and both write to the same `.next` directory, so a build wipes the manifests out from under the dev server. It then throws `ENOENT ... build-manifest.json` on every request until you restart it. Use `npm run typecheck` instead: it checks the same types and never touches `.next`.

No automated test suite is configured (no jest/vitest setup) — verification is manual in the browser, against the real grill. To watch or fake MQTT traffic while developing, use `mosquitto_sub -v -t 'grill/#'` and `mosquitto_pub` directly against the broker.

Without the grill, `npm run fake-grill` (`scripts/fake-grill.mjs`) stands in for the ESP32 against a local broker on `mqtt://localhost:1883` (`MQTT_URL` overrides it). It publishes the LWT, mode and reset status, moves position and rotation for real on `set_position`, `set_rotation` and the manual commands, sends a temperature every 5 s, and answers on `status/result`. It also runs programs: it steps through them in the firmware's order, publishes the retained `status/program/current`, and honours `skip_step`, `edit_step` and `cancel`. A temperature step just waits 5 s. Without the database to list programs, `npm run fake-program -- <0|1> [cancel]` starts a demo one on that grill (left by default), or cancels it. The broker needs a WebSocket listener on 1884 and `allow_anonymous true`, and the web needs `MQTT_HOST=localhost` — or start the `nextjs-dev-fake-grill` config in `.claude/launch.json`, which runs the dev server with `MQTT_HOST=localhost` and leaves `.env.local` pointing at the real grill. A `localhost` broker is also what turns on the client's simulation shortcuts (`isLocalBroker` in `useMqtt`). With no database reachable, the user modal does not open and the control page still works.

## Architecture

- **The API lives in this project.** `src/app/api/**/route.ts` only handles HTTP; bodies are validated with `zod` (`src/server/validation/`), queries live in a data access layer (`src/server/data/`) built on Drizzle, and `src/db/` holds the `mysql2` pool and the schema, written by hand because `drizzle-kit pull` hangs on MariaDB's `json_valid` check. Everything under `src/server/` and `src/db/` imports `server-only`, so a client component that pulls it in fails the build instead of shipping the credentials. Responses keep the exact snake_case shape the old FastAPI service sent. See [docs/api.md](docs/api.md) and [docs/database.md](docs/database.md).
- **The broker's address comes from the server.** The page is no longer served from the Home Assistant host, so `location.hostname` cannot find the broker. The root layout reads `MQTT_*` (`src/server/mqttConfig.ts`) and passes them through `Providers` to `MqttProvider`; an empty `MQTT_HOST` still falls back to the page's host. The password reaches the browser either way, as it did when it was `NEXT_PUBLIC_`: the broker's WebSocket needs it from there.
- **`homeassistant/dashboard-card.yaml`** is the HA dashboard view that embeds this app in an iframe, pasted into the dashboard's raw config editor by hand. Its URL names the home lab's fixed address, which the browser resolves, so the card only works from the LAN.
- **Who made a program** is a row in the `users` table, not free text. `CurrentUserContext` fetches `GET /api/users`, keeps the pick in `localStorage` under `gaztaindigrill.user`, and validates the stored id against that list on every load — a user deactivated since is dropped and the modal reopens. `UserSelectionModal` is mounted in `providers.tsx` and cannot be dismissed until a user is picked, since nothing in the app works without one; the FAB's `Cambiar usuario` reopens it later, and that one *is* dismissable. Programs carry `userId` and read the creator's name from the API's joined `userName`. The `creatorName` still in `RunningProgram` and the execute payload is the MQTT side, which was deliberately left alone.
- **HTTP to `/api`** is used *only* for CRUD on programs, categories and users, always on the page's own origin (`fetch('/api/programs')`). See [docs/api.md](docs/api.md) for the request/response shapes — note the camelCase-request / snake_case-response asymmetry, which the pages already expect.
- **MQTT directly to the grill** (not routed through the API) handles everything real-time: manual movement/rotation commands, program execution, sensor telemetry, mode switching, and online/offline connection state. [docs/mqtt.md](docs/mqtt.md) documents the whole contract — topic tables, the `{ value, requestId }` envelope, error codes, flows. The topic strings themselves are owned by the firmware's `GrillConstants.h` and mirrored in `src/constants/mqtt.ts`; on any disagreement the firmware wins.
- **Running-program state** (`src/contexts/RunningProgramsContext.tsx`): there is no cache and no request/response round trip. The ESP32 publishes the *entire* running program (name, steps, `currentStepIndex`, `stepStartUnix` on the current step) **retained** on `grill/{id}/status/program/current`, so the broker hands it to any client the moment it subscribes. The context just stores that payload per grill index and nulls it on `{ isRunning: false }`. See [docs/cache.md](docs/cache.md).
- **`src/hooks/useMqtt.tsx`** — core MQTT client hook (uses the `mqtt` package). Domain-specific hooks (`useGrillState`, `useGrillCommands`, `useSystemActions`) build on top of it for grill state and command dispatch.
- **Contexts** (`src/contexts/`): `GrillStateContext` (live state per grill), `CurrentModeContext` (single vs dual grill mode), `RunningProgramsContext` (the cache above), `CurrentUserContext` (who is using the app).
- **Routes** (`src/app/`): `control/` (manual + program execution control surface, with `ControlPad`, `ProgramExecutionStatus`, execution detail/step views), `programs/` (create/edit/list programs, with category and step modals), `mode/` (single/dual mode switching).
- **3D grill visualization** (`src/components/three/`) uses `@react-three/fiber`/`drei`/`three`. There is **one `<Canvas>` for the whole app**, owned by `SharedGrillCanvasProvider` in `providers.tsx`: each scene component (`GrillScene`, `SimulatorScene`) is only a sized slot that hands the canvas the model to draw, and the canvas is moved in the DOM into the slot mounted last, so the modal takes it over the page and hands it back on close. Each model has one job: `GrillModel` shows the real grills from MQTT and handles tapping and dragging; `SimulatedGrill` only draws the left grill at a pose it reads every frame. What both need to know about the `.glb` lives in `grillRig.ts`: the model path, node names, height per percent, the focus camera and the greyed-out material. A canvas per scene rebuilt the WebGL context, the shaders and the environment every time, which is what made the modal slow to open and close. drei's `<View>` was rejected: its canvas sits over the whole page, so the page's view would paint over the modals' backdrops, and the modal's drag listens on `gl.domElement`. The lighting comes from a 256 px `.hdr` in `public/hdri/`; it only lights the model, so a larger one buys nothing. `grillRig.ts` looks grills up by node name (`padre_parrilla_ezkerra`/`eskubi`, and `rotor_cilindro+parrilla` for the tilt), so renaming them in Blender breaks both scenes. `GrillModel` is also the only way to set a height on `/control`: tapping a grill opens `GrillPositionModal`, which renders the whole model with everything but that grill greyed out and see-through (corner camera for the left one, so the tilt shows; front camera for the right one, both framing the rack's full travel with margin) The height being picked is a solid copy of that grill that follows the pointer in 5 % steps, while the grill at its real height fades out. On the left grill an `Altura | Giro` selector says which of the two the drag moves, and the copy tilts with the picked angle. Two text fields over the scene hold the same targets: dragging rewrites them, and typing moves the copy, so any value can be reached exactly. A red slab marks the heights a rack at that tilt may not stay at — `minSafePosition()` in `src/utils/rotation.ts` mirrors the firmware's own floor, so both change together. "Mover" sends `set_pose` with height and tilt on the left grill, or `set_position` when the tilt is unchanged, and `set_position` on the right one. In dual mode either grill opens grill 0. The modal and the pads stay usable while a program runs, so the height can be nudged mid-cook; only an offline grill locks them. The firmware still refuses `set_pose` and the rotor zero (`rotor_busy`) during a program, so a tilt change from the modal fails then and the zero button stays disabled.
- **Program simulator** (`ProgramSimulator` in `app/programs/components/`, always shown under the steps on create and edit, with Start disabled until there is one): replays the program on the left grill in 3D, with start/pause, skip step, restart, speeds x1/x5/x10/x20 and, for relative programs, a starting height that follows the real one until it is typed over (the "Altura actual" button goes back to following it). `planSimulation()` in `src/utils/programSimulation.ts` turns the steps into timed phases following the firmware's own rules: the step type in `ProgramManager`'s order, relative heights added to the start and clamped to 0-100, the tilt's floor under any height, and the rotation guard's lift, short-way turn and return (`minSafePositionForTurn()` and `rotorTurn()` in `src/utils/rotation.ts`). Skipping ends the step at its final pose, unlike the firmware, which stops the motor where it is. There is no fire model: a temperature step waits until it is skipped. The speeds (8 %/s, 30 °/s) are guesses shared with `scripts/fake-grill.mjs`, not measured. `useProgramSimulation` owns the clock; the 3D grill pulls `getPose()` every frame, so the animation does not re-render React. The starting point lives in `useSimulationStart`, owned by `ProgramForm`, so the simulator and the step modal start from the same place. `planSimulation()` also takes `hasRotor` (false for the right grill: turns and flips do nothing and there is no tilt floor) and `anchor` (where a relative program started, when that is not the simulation's start).
- **Editing a running program** (`ProgramExecutionStatus` on `/control`): a pencil on each future step and on the wait under way (never an action) opens the same `StepModal`, with `lockedType` and no preview, and sends `action/program/edit_step`. The change lives only in the ESP32's RAM for that run; the saved program in the API is untouched. The firmware only checks the index, so which steps may be edited, and that their type stays, is the client's rule. The wait under way opens with the time it has left (`secondsSince()` on its `stepStartUnix`, or its whole duration without an NTP date), and on save the firmware starts that wait again, so the value typed is what is left from now. The step ⇄ form conversion both pages use lives in `app/programs/utils/stepForm.ts`.
- **Running-step notices** (`useRunningStepNotices` in `app/control/hooks/`): each step still to run on `/control` carries the simulator's notice — amber when it will not do what it says, grey for the lift before a turn. It simulates from the current step and from the grill's live pose, so moving the grill by hand mid-program updates the steps ahead at once. The step under way keeps the notice it had when it started: the firmware fixes a height's floor when the step begins (`MovementManager::go_to()`), and a lift before a turn would otherwise stop being announced halfway up. Relative programs add their steps to the firmware's `positionAnchor`. While a temperature is held the height follows the fire, so those notices end in "(aproximado)". The edit modal shows the same notice for the value being typed. `SelectGrillModal` runs the same simulation from each grill's pose but only says that some step will not run as written and that the details are on `/control`. `useSimulatedGrill()` decides whose pose and rotor count: in dual mode, the left grill's for both.
- **Step preview** (`StepPreview`, inside `StepModal` for position and rotation steps): shows the left grill where the step being typed leaves it, simulated after the steps before it (all of them when adding, those above it when editing), with the same notices as the simulator's list — a height cut to 0-100, the tilt's floor, and the lift before a turn. It borrows the shared canvas while the modal is open. A rotation of `ROTATION_WRAPS_AT` (356°) or more becomes 0° as it is typed, since the firmware refuses 360 and above.
- Import alias `@/*` → `src/*` (see `tsconfig.json`). The `eslint-plugin-no-relative-import-paths` lint rule is enabled — prefer the `@/` alias over relative imports across directories.
